## このスキルがやること

日本語のコメント・docstring・文字列リテラルを英語に翻訳し、レビューを経てコミットする。翻訳される元のコード（処理ロジック）が正しいかどうかはこのスキルの関心事ではない。文面を直すことだけが仕事なので、ロジックのバグに気づいても指摘に留め、勝手に直さない。

## 手順

### 1. 対象を集める

**引数が渡された場合**: 引数はファイルまたはディレクトリのパスとして扱う。git管理下にあるかどうか、変更があるかどうかに関わらず、指定されたパスの内容全体を対象にする。

**引数がない場合**: カレントディレクトリで以下を実行し、未コミットの変更をすべて洗い出す。

```
git status
git diff
git diff --cached
```

対象は staged / unstaged / untracked の新規ファイルすべて。untracked ファイルは中身をそのまま読む（diff には出てこないため）。

対象がなければ（未コミットの変更もなく、引数も渡されていなければ）、その旨をユーザーに伝えて終了する。

### 2. 日本語部分を見つけて翻訳する

対象の中から、次に該当する箇所を探す:

- コメント（`//`, `#`, `/* */` など）
- docstring / JSDoc など
- 文字列リテラル（ログ出力、エラーメッセージ、例外メッセージ、CLI の出力文言、UI表示文言など）

対象外:

- 変数名・関数名・クラス名などの識別子（日本語識別子があっても変更しない）
- コードの処理ロジックそのもの

自然で簡潔な技術文書英語に翻訳する。直訳ではなく、OSSのコードベースで違和感のない言い回しを選ぶ。i18n/localeファイルなど「日本語であること自体が仕様」のファイルを見分ける特別な除外ロジックは実装しない — 対象範囲に入っていればそのまま翻訳対象にする。

### 3. まとめてレビューしてもらう

該当ファイルすべてに翻訳を適用したら、変更後の diff を一括でユーザーに提示し、レビューを依頼する。

- ユーザーが「ここは違う」と部分的に指摘した場合は、指摘箇所だけを直して再度 diff を提示する。これを承認が得られるまで繰り返す。
- ユーザーが全体的にやり直しを求めた場合はその指示に従う。

### 4. 承認されたらコミットする

承認が得られたら、変更したファイルを `git add` してコミットする。複数ファイルにまたがっていても、1つのコミットにまとめる。コミットメッセージは変更内容を要約したもの（例: `Translate Japanese comments and strings to English`）にし、通常のコミット作法（HEREDOC 経由、Co-Authored-By 行を含める等）に従う。

git worktree は切らない。呼ばれたディレクトリでそのまま作業する。
