質問をする際は`AskUserQuestion`ツールを用いて質問すること。

### 質問設計のルール

- 設計判断・実装方針を問う質問は、必ず先頭の選択肢を「推奨案（Recommended）」にし、
  推奨理由・トレードオフを`description`に書く。選択肢を並べるだけで判断を丸投げしない。
- 選択肢には毎回「わからない・一緒に考えたい」を含める。
  選ばれたら、その場で壁打ちはせず質問を打ち切る。
  該当する設計判断は「〇〇の方式を調査・決定する（実装時に検討）」という
  タスクとしてタスクリストに積み、先へ進む。
  実装方式の細部検討は着手時の壁打ちに委ねる（このスキルの役割ではない）。
- ユーザーが答えを持っていなさそうな不明点（未着手の設計判断、外部要因待ちなど）は、
  選択肢を出す前に一旦「これは決まっていない可能性がある」と考え、
  該当タスクは決定自体をタスク化する（例:「〇〇の方式を決定する」）のも選択肢に含める。

## 概要

現在のブランチで進めている作業を、実装可能な粒度のタスクリストに分解し、
`docs/task/{branch}-task.md` にチェックボックス形式で保存する。

「今どこにいるか」はタスクリストの中の最初の未チェック項目そのものとして扱う。
別途「現在地」セクションは作らない。

## フェーズ1: 対象の特定

1. `git branch --show-current` で現在のブランチ名を取得する
2. `$ARGUMENTS` に issue番号・URL があれば `gh issue view` で内容を取得する
3. 指定がなければ、会話で目的・背景を一つずつ質問して聴き取る
   - 「このブランチで最終的に何を達成したい?」
   - 「完了条件は何?」

## フェーズ2: コードベース調査

Explore等で関連ファイル・既存実装を把握する。
調査で埋まらない不明点だけ、ユーザーに一つずつ質問する。

## フェーズ3: タスク洗い出し

- タスクは `file:line` レベルまで具体化する
- 実装順に並べる
- 既に `docs/task/{branch}-task.md` が存在する場合は読み込み、
  完了済み(`- [x]`)のタスクは維持したまま、未完了分を見直し・追記する

## フェーズ4: 保存

「これを保存していい?」と確認してから、以下のフォーマットで
`docs/task/{branch}-task.md` に保存する。

```markdown
---
branch: {branch}
issue: #42 (なければ省略)
created: {YYYY-MM-DD}
updated: {YYYY-MM-DD}
---

# {branch} タスク

## 目的

{何をなぜやるか}

## タスク

- [x] {完了タスク} (`path/to/file.ts:42`)
- [ ] {次にやるタスク}
- [ ] {未着手タスク}

## 完了条件

{Doneの定義}
```

## 進捗の更新

保存はゴールではなく開始点。実装を進める中で、タスクが完了するたびに
`docs/task/{branch}-task.md` の該当行を `- [ ]` → `- [x]` に手動で更新する。
このスキルを再実行したときは、既存のチェック状態を壊さず、
残タスクの見直し・追記のみ行う。

## 禁止事項

- 一度に複数の質問を並べない
- ユーザーが確認していないのに保存しない
- 「現在地」のような別セクションを新設しない（チェックボックスの状態が現在地）
- 完了済みタスクのチェックを無断で外さない
