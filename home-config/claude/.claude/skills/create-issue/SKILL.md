## このスキルがやること

Issueにしたい内容から、タイトル・本文・ラベルの案を作る。
ユーザーの承認を得てから、`gh issue create` で1件作成する。
ブランチの作成や実装はしない。
複数のIssueを作るときは、1件ずつ、手順 2 から繰り返す。

## 手順

### 1. 事前チェック

```
gh auth status
git remote get-url origin
```

`gh` が未認証なら、「`gh auth login` が必要です」と伝えて終了する。
origin が `github.com` を指していなければ、その旨を伝えて終了する。

### 2. 題材を確認する

`$ARGUMENTS` と直前の会話から、Issueにしたい内容を読み取る。
題材が曖昧で複数の解釈が成り立つ場合は、決めつけずにユーザーへ確認する。

### 3. コードを確認する

題材に関係するファイルを `Read` して、事実を確認する。
コードを読めば確定する事実は、ユーザーに質問しない。

### 4. 重複を確認する

```
gh issue list --state open --limit 100 --json number,title
```

類似するIssueがあれば、番号とタイトルを提示して、作成を続けるか確認する。

### 5. テンプレートとラベルを確認する

Issue テンプレートがあれば、それを優先する。

```
ls .github/ISSUE_TEMPLATE .github/ISSUE_TEMPLATE.md .github/issue_template.md 2>/dev/null
```

- 該当するテンプレートが1つなら、その見出し構成に沿って本文を書く。
- 複数あれば、題材に合うものを選ぶ。判断できなければユーザーに聞く。
- テンプレートの `labels` や `title` の指定があれば従う。
- テンプレートがなければ、手順 6 の既定の書式を使う。

ラベルは `gh label list` の既存ラベルから選ぶ。
新しいラベルは作らない。

### 6. 案を作る

既定の書式（テンプレートがない場合）。

```
## 背景

<なぜこのIssueが必要か>

## やること

- [ ] <作業項目>

## 完了条件

- <Done の定義>
```

- 言語は日本語にする。
- 句点（`。`）の後で改行する。
- タイトルに `feat:` などのプレフィックスは付けない。
- 実装済みの機能として書かない。コードで確認した事実だけを事実として書く。
- 確認済みの事実と、推測による記述を区別する。推測を含む場合は、案の下に「〇〇は推測です」と明記する。
- 機能のアイデアや改善案は、Issueの本文に含めてよい（ドキュメントではなくIssueで管理する方針のため）。

### 7. 案を提示して確認を得る

タイトル、ラベル、本文を表示し、ユーザーの自由入力の返答を待つ。
他のスキル（例: `pr-review`）から呼ばれた場合も、この手順は省略しない。

- 承認（「OK」「ok」「はい」「LGTM」「お願いします」など）なら手順 8 に進む。承認かどうか曖昧な返答は、作成せずに聞き返す。
- それ以外は修正指示として扱う。指示を反映して再提示し、承認を得るまで繰り返す。

### 8. 作成する

本文を scratchpad のファイルに書き出し、`--body-file` で渡す。

```
gh issue create --title "<タイトル>" --label "<ラベル>" --body-file <本文ファイル>
```

ラベルが複数なら `--label` を繰り返す。
ラベルがなければ `--label` は付けない。

### 9. 報告する

Issue の番号、URL、付与したラベルを報告する。

### 10. 作成が失敗したとき

エラー内容をそのまま報告する。
原因が自動で直せる場合（存在しないラベル名など）は、修正案を提示して承認を得てから再実行する。
承認なしにリトライしない。

## その他

- git worktree は切らない。呼ばれたディレクトリでそのまま作業する。
