# PR Review モード

## 概要

コードの変更内容を読み解き、**意図・設計判断・実装漏れ**を一緒に壁打ちしながら、実装に対するレポート出力を行い、質の高いPR下書きを作る。

選択肢のある質問をする際は`AskUserQuestion`ツールを用いて質問すること。

---

## 事前チェック

```bash
git status
```

- Gitリポジトリでなければ「Gitリポジトリが見当たりません」と伝えて終了。

### 基準ブランチ

差分の基準はローカルの `main` ではなく、リモートの `origin/main` とする。
ローカルの `main` が古いと、すでにマージ済みのPRのコミットが差分に混ざるため。

```bash
git fetch origin main
```

- 以降の `git log` / `git diff` は、すべて `origin/main..HEAD` を基準にする。
- `git fetch` に失敗した場合は、その旨をユーザーに伝え、古い `origin/main` を基準にしていることを明記して続行する。

```bash
git log origin/main..HEAD --oneline
```

- コミットがなければ「コミットが見当たりません。先にコミットを作成してください」と伝えて終了。

---

## フェーズ1: 変更の把握

以下のコマンドを実行し、変更の全体像を掴む。ユーザーへの確認不要。

```bash
git branch --show-current
git log origin/main..HEAD --oneline
git diff origin/main..HEAD --stat
git diff origin/main..HEAD
```

差分だけで判断せず、以下の周辺情報も確認する。
指摘の根拠にするため、フェーズ3に入る前に済ませておく。

- 静的検査: プロジェクトの型チェック・lint・ビルドを実行し、結果を確認する。
- 呼び出し元: 追加・変更した関数・型・モジュールが、どこから使われているか（使われていないか）を検索する。
- 関連する定義: DBスキーマ・マイグレーション・設定ファイル・環境変数など、変更の前提となるファイルを読む。
- 既存テスト: 変更箇所に対するテストの有無と、何を検証しているかを確認する。

把握した後、以下の観点で**自分なりの読み解き**を示す:

- **何を変えたか**: ファイル・関数・設定の変更一覧
- **変更の規模感**: 小さな修正 / 機能追加 / リファクタ / 破壊的変更
- **変わった構造や流れ**: 関数の切り出し・依存関係の変化など

読み解いた内容を示し「この解釈でよろしいか？」と一言確認してからフェーズ2へ。

---

## フェーズ2: 意図・設計の壁打ち

変更ごとに**なぜそうしたか**を一緒に掘り下げる。

### 問いかけの観点

- **意図の確認**
- **設計判断の確認**

### 進め方のルール

- **一度に一つだけ問う**。矢継ぎ早に問わない。
- 内容を要約して確認しながら進む。
- ユーザーが「わからない」と言った場合は、自分なりの見立てを仮説として示す。
- 十分に掘り下げたと判断したら、次の観点に進んでよいか聞く。

---

## フェーズ3: 5観点レビュー

壁打ちで得た情報をもとに、以下の5つの軸で指摘事項を収集する。

### 指摘の根拠ルール

- 指摘は、コード・設定・実行結果などの根拠を確認してから書く。
- 根拠を確認できたものは「確認済み」とし、確認方法（読んだファイル・実行したコマンド）を明記する。
- 根拠を確認できていないものは「推測」とし、重要度は 🟢 Low 以下にする。または確認してから指摘する。
- 推測を断定口調で書かない（「〜になります」ではなく「〜の可能性があります」と書く）。
- 呼び出し元がなく実害が確認できないものは、🔴 High にしない。
- チェックリストの項目を埋めるために指摘をひねり出さない。該当がない軸は「指摘なし」と書いてよい。
- ユーザーが指摘の根拠に疑問を示したら、自分で再確認し、誤りなら速やかに取り下げて件数を更新する。

---

### 軸1: セキュリティ

- 入力値の検証・サニタイズは十分か（SQLインジェクション・XSS・コマンドインジェクション等）
- 認証・認可のチェックが漏れていないか
- シークレット・APIキー・パスワードがコードやログに露出していないか
- 外部入力をそのまま使っている箇所はないか
- 依存ライブラリに既知の脆弱性はないか

---

### 軸2: 可読性・保守性

- 変数名・関数名・クラス名は意図を正確に伝えているか
- 関数・モジュールの責務が明確に分離されているか（単一責任）
- 重複したロジックが生まれていないか
- 将来の変更を困難にする密結合・隠れた依存はないか
- 複雑なロジックに必要最低限のコメントがあるか（WHYが書かれているか）

---

### 軸3: パフォーマンス

- ループ内でのDB・API呼び出し（N+1問題）は発生していないか
- 不要な再計算・再レンダリングが発生していないか
- メモリリーク・リソース解放漏れはないか
- 大量データ処理でのページネーション・ストリーミングの考慮は十分か
- キャッシュが効果的に使われているか（あるいは無効化が正しく行われているか）

---

### 軸4: 影響範囲

- 既存機能・他モジュールへの破壊的影響はないか
- 型定義・インターフェース変更の整合は取れているか
- 設定ファイル・環境変数・マイグレーションの変更漏れはないか
- 一つのPRに詰め込みすぎていないか（責務が混在していないか）
- 外部APIやDBスキーマの変更を伴う場合、後方互換性は確保されているか

---

### 軸5: エラーハンドリング

- 例外・エラーが適切にキャッチ・処理されているか
- エラー時にリソースが正しく解放されるか（ファイル・DB接続・ロック等）
- エラーメッセージは原因特定に十分な情報を含んでいるか
- 外部API・DBのタイムアウト・リトライ処理は考慮されているか
- ユーザーへのエラー通知が内部情報を漏らしていないか

---

## フェーズ4: 重要度スコアリング

各指摘に以下のいずれかを付与する。

| 重要度    | 基準                                                                           |
| --------- | ------------------------------------------------------------------------------ |
| 🔴 High   | 下記の「致命的」に該当する(アプリが壊れる・データが失われる・不可逆的な副作用) |
| 🟡 Medium | 今は動くが、あとから技術的負債として跳ね返ってくる(設計・保守性・テスト不足)   |
| 🟢 Low    | 修正しなくても実害はないが、実施すると品質が向上する(スタイル・些細な改善)     |

### 区分

重要度とは別に、各指摘を次の3区分のいずれかに分類する。
区分は、この指摘をこのブランチで直すべきか、Issueにして別ブランチで直すかを決めるために使う。

| 区分     | 基準                                                                                     | 既定の扱い                                              |
| -------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 致命的   | 下記の基準1〜4のいずれかに該当し、かつ実際に起きることをコードや実行結果で確認できたもの | ブランチ内で修正する                                    |
| 要判断   | パフォーマンス・UXなど、度合いによって致命的かどうかが変わるもの                         | 推奨を示し、ユーザーが決める                            |
| 非致命的 | アプリは壊れないが、改善したほうがよいもの                                               | 下記の基準で、ブランチで修正するかIssueにするかを決める |

致命的の基準:

1. アプリが起動しない、主要な操作が完走できない、クラッシュする。
2. ユーザーのデータが消える、壊れる、他人に見える。
3. 認証・認可の突破や、シークレットの漏洩などのセキュリティ事故。
4. 元に戻せない副作用(本番DBの破壊的マイグレーションなど)。

- 重要度が High の指摘は、必ず「致命的」に区分する。基準1〜4に当てはまらないものを High にしない。
- 「要判断」には、判断材料(実測値・影響範囲・再現条件)を必ず添える。
  - 例: 「操作時に2秒フリーズする」なら致命的寄り、「レイテンシーが0.3秒悪化する」なら非致命的寄り。
  - 度合いの判断は人間が行う。Claudeは区分と推奨を提案するだけで、決めつけない。

### ブランチで直すか、Issueにするか

重症度ではなく、修正の性質(責務を分けるべきか)で決める。
既定は「ブランチで修正」とする。

次のいずれかに当てはまるときだけ「Issueにする」。

1. このブランチで変更していないコードの問題である(既存の負債、他機能の不具合)。
2. 修正が別の責務・別の機能に及ぶ。または設計変更を伴い、独立したPRとしてレビューすべき規模である。
3. 修正に事前の計測・調査・仕様の議論が必要で、このPRの範囲では結論が出ない。

次のものは、重症度が低くてもブランチで修正する。

- このブランチで追加・変更したコードの、可読性・型・重複・ドキュメントの不備。
- 数行〜数十行で直り、Issue・ブランチ・PRを作る手間のほうが大きい修正。

---

## フェーズ4.5: 振り分け

フェーズ4の後、レポートを出力する前に、全指摘の振り分け案を1つの一覧で提示する。
質問は1件ずつ行わず、一覧への返信1回で確定させる。

### 一覧の書式

| #   | 指摘の要約 | 区分     | 推奨           | 判断材料 |
| --- | ---------- | -------- | -------------- | -------- |
| 1   | ...        | 致命的   | ブランチで修正 | ...      |
| 2   | ...        | 要判断   | Issueにする    | ...      |
| 3   | ...        | 非致命的 | ブランチで修正 | ...      |

- 「推奨」は「ブランチで修正」か「Issueにする」のどちらかに必ず倒す。「要判断」でも保留にしない。
- 「推奨」は上の「ブランチで直すか、Issueにするか」の基準で判定し、どの基準に当てはまったかを「判断材料」に1行で書く。
- ユーザーは、変更したい番号だけを返す(例: 「2はブランチで修正」)。
- 何も返信がなければ、推奨どおりに確定する。
- 「致命的」と判定した指摘も、ユーザーが「Issueにする」に変更できる。

---

## フェーズ4.6: Issue作成

振り分けが確定したら、「Issueにする」と決まった指摘をGitHub Issueにする。
ユーザーの確認なしにIssueを作成しない。
「Issueにする」と決まった指摘が0件の場合は、このフェーズを省略してフェーズ5に進む。

`AskQuestion`を使用して質問してください。

1. 作成するIssueの件数とタイトルの一覧を見せ、作成してよいか確認する。
2. 承認されたら、指摘1件ずつ `create-issue` スキルを実行して作成する。
3. 作成したIssueの番号を、各指摘に紐づけて記録する。後続のレポートで使う。

### Issueの単位

- 1指摘 = 1 Issue とする。指摘ごとに別ブランチで直せるようにするため。
- 同じ原因の指摘が複数ある場合だけ、1つのIssueにまとめる。

### create-issue への引き継ぎ

Issueの言語・書式・ラベル・重複確認は、すべて `create-issue` の手順に従う。
`gh issue create` を直接実行しない。

`create-issue` を呼ぶときは、次の内容を伝える。

- この呼び出しは `pr-review` からで、手順2の一覧でユーザーの承認を取得済みである。
  - そのため `create-issue` の手順7(案の提示と承認)を省略する。
- 題材として、次の情報を渡す。
  - ブランチ名: 本文に ref として書く。PRは書かない(Issue作成時点でPRが存在しないため)。
  - 場所(`ファイルパス:行`)
  - 指摘内容
  - 根拠(確認済みか推測か)
  - 修正案
- 重要度や軸は、Issueに書かない。

---

## フェーズ5: レポート出力

Planモードを抜けて、フェーズ4.6のIssue作成が終わった後に、以下のレポート出力を行う。
Issueにした指摘には、作成したIssueの番号(`#番号`)を記載する。

```
## /pr-review: <title>

### 指摘事項（<件数> 件）

#### 1. `<ファイルパス>`（<そのファイルの件数> 件）

| Index | 重要度    | 軸  | 場所 | 指摘内容 | 根拠                 | 修正案                   |
| ----- | --------- | --- | ---- | -------- | -------------------- | ------------------------ |
| 1-1   | 🔴 High   | ... | ...  | ...      | 確認済み（確認方法） | ...                      |
| 1-2   | 🟡 Medium | ... | ...  | ...      | 確認済み / 推測      | ... (Issue化済み: #番号) |

#### 2. `<ファイルパス>`（<そのファイルの件数> 件）

| Index | 重要度    | 軸  | 場所 | 指摘内容 | 根拠                 | 修正案                   |
| ----- | --------- | --- | ---- | -------- | -------------------- | ------------------------ |
| 2-1   | 🔴 High   | ... | ...  | ...      | 確認済み（確認方法） | ...                      |
| 2-2   | 🟡 Medium | ... | ...  | ...      | 確認済み / 推測      | ... (Issue化済み: #番号) |

### 総評
**マージ可** ✅  ← 「ブランチで修正」と決まった指摘が 0 件の場合
または
**要修正** ❌ （ブランチで修正: N 件、Issue化: M 件）← 「ブランチで修正」と決まった指摘が 1 件以上の場合


```

マージ可否は、「ブランチで修正」と決まった指摘の件数だけで判定する。
0 件であれば「マージ可」、1 件以上であれば「要修正」とする。
Issueにした指摘は、マージ可否の判定に含めない。

### ファイル別の列記ルール

- 指摘はファイル単位の見出しでまとめ、そのファイルの指摘を表に並べる。
- ファイルの並び順は `git diff origin/main..HEAD --stat` の順とする。
- 同一ファイル内の指摘は、重要度の高い順（High → Medium → Low）に並べる。
- 複数ファイルにまたがる指摘は、主因となるファイルの表に書き、指摘内容に関連ファイルを明記する。
- 指摘のないファイルは、見出しの下に「指摘なし」と書く。表は作らない。
- 生成物・ロックファイルなど、レビュー対象外としたファイルは、末尾に「対象外: <ファイル名>（理由）」とまとめて書く。

### レポートの保存

ターミナルへ出力したレポートと同じ内容を、Markdownファイルとして保存する。
ただし保存ファイルでは表を使わず、下記の「保存ファイルの書式」に従う。
保存先は本体リポジトリの `.git` 直下とし、コミット対象や `.gitignore` に影響させない。
worktree で実行しても、全worktreeのレビューが本体の `.git` に集まる。

```bash
dir="$(git rev-parse --path-format=absolute --git-common-dir)/pr-reviews"
mkdir -p "$dir"
branch="$(git branch --show-current | tr '/' '-')"
file="$dir/${branch}_$(date +%Y-%m-%d_%H%M).md"
```

- ファイル名は `YYYY-MM-DD_HHMM_{ブランチ名}.md` とする。
- 保存後、ファイルの絶対パスをテキストで表示する（`file://` は付けない）。

#### 保存ファイルの書式

- 指摘事項の表は使わず、指摘ごとに見出しと箇条書きで書く。
- ファイル別の見出し（`#### <ファイルパス>（N 件）`）の下に、指摘ごとの見出しを `##### <重要度絵文字> <重要度>: <指摘の要約>` の形で置く。
- 指摘の見出しの下に、次の項目を箇条書きで書く。
  - 軸
  - 場所
  - 指摘内容（複数文は入れ子の箇条書きにし、句点で改行する）
  - 根拠（確認済み / 推測）
  - 修正案
  - 修正確認: 「ブランチで修正」と決まった指摘は `- [ ] 修正済み`（未修正は `[ ]`、修正済みは `[x]`）
  - Issue化: 「Issueにする」と決まった指摘は、修正確認の代わりに `- Issue化済み: #番号` と書く（チェックボックスは付けない）
- 指摘のないファイルは、見出しの下に「指摘なし」とだけ書く。
- 「実行結果」「総評」は、見出し付きの箇条書きで書く。
- 総評の行には、High / Medium / Low の件数を併記する。
- ターミナルへの出力は、従来どおり表形式でよい。

#### 修正確認チェックボックスの運用

- 保存時は、「ブランチで修正」と決まった指摘を `- [ ] 修正済み` で出力する。
- 「Issueにする」と決まった指摘は、チェックボックスではなく `- Issue化済み: #番号` で出力する。
- フェーズ8の再レビューで修正を確認できた指摘は、元の保存ファイルの該当チェックボックスを `[x]` に更新する。
- 未修正・新規の指摘は、フェーズ8の再レポートに従い新しい日時のファイルへ `[ ]` で保存する。

## フェーズ8: 修正・実装チェック

ユーザーのレポート指摘事項の修正完了報告を待つ。
「ブランチで修正」と決まった指摘が修正されたかを確認し、新規・未対応事項があれば再度以下のフォーマットでレポート出力を行う。

- Issue化した指摘は再確認も再掲もしない。再レポートと保存ファイルから除外する。
- 新規の指摘が見つかった場合は、フェーズ4.5の振り分けを行ってから、再レポートを出力する。

```
# /pr-review: <title>

## 指摘事項（<件数> 件）

### `<ファイルパス>`（<そのファイルの件数> 件）

| 重要度 | 軸 | 場所 | 指摘内容 | 根拠 | 修正案 |
|---|---|---|---|---|---|
| 🔴 High | ... | ... | ... | 確認済み（確認方法） | ... |
| 🟡 Medium | ... | ... | ... | 確認済み / 推測 | ... |

## 総評
**マージ可** ✅  ← High が 0 件の場合
または
**要修正** ❌ （ブランチで修正: N 件）← 未修正の「ブランチで修正」の指摘が 1 件以上の場合


```

マージ可否の判定は、フェーズ5と同じく、未修正の「ブランチで修正」の指摘の件数だけで行う。
ファイル別の列記ルールはフェーズ5と同じとする。
再レポートもフェーズ5の「レポートの保存」と同じ手順で、新しい日時のファイルとして保存し、絶対パスを表示する。

## フェーズ7: PR下書き作成

指摘事項がなくなった時点でPR下書き作成を行う。
Planモードで以下のフォーマットでPR下書き作成を行う。

### 下書きフォーマット

- **英語**で記述する
- **命令形・動詞始まり**で書く（例: "Add", "Create", "Sets up..."）。体言止め・名詞句の羅列にしない
- **冗長にしない**。1文は簡潔に、説明が不要な自明な変更は書かない
- 各セクションは1〜数文 + 箇条書きで済ませ、長い段落を作らない
- Design Decisions / Notesには、**実装したコードから読み取れる判断**と、**今後の変更に影響する点**だけを書く
  - 書くもの: 以前の挙動や設計から決定的に変わった点、今後の変更で守る必要がある前提(座標系・保存される内容・仕様上の制限など)、一見バグに見えるが意図した挙動
  - 書かないもの: 採用しなかった案とその却下理由(コードに現れない)、「こうリファクタリングできる」「将来こうできる」といった実装に対する感想や展望
  - 壁打ち(フェーズ2)で確認した意図のうち、上に当てはまるものだけを反映する。壁打ちで話題に出ただけで、コードに現れないものは書かない
- フェーズ3で拾った5観点の指摘のうち、**マージ後もレビュアーが意識すべき点だけ**をReview Focusに残す（フェーズ8で解消済みの軽微な指摘は書かない）
- Issueにした指摘は、Known Issues / Out of Scopeに `#番号` つきで列挙する

```markdown
## Summary

{1〜2文で、このPRが何をするか}

## Background / Motivation

{なぜこの変更が必要か。課題・文脈を簡潔に}

## Changes

{変更点を箇条書きで具体的に。ファイル単位でまとめてよい}

- Add {対象}: {概要}
- Create {対象}: {概要}

## Design Decisions / Notes

{コードから読み取れる設計判断と、今後の変更に影響する点。採用しなかった案は書かない}

- {以前から変わった点、またはこのコードの前提とその理由}
- {今後の変更で守る必要がある点}

## Review Focus

{5観点のうち、レビュアーが特に注意すべき点のみ簡潔に}

- **{観点}**: {内容}

## Known Issues / Out of Scope

{今回対応しなかった事項と理由。Issueにした指摘は #番号 つきで列挙する}

- #{Issue番号}: {指摘の要約}
```

### gh コマンドでの作成

```bash
gh pr create \
  --title "{タイトル}" \
  --body "{上記フォーマット}" \
  --draft
```

- `--draft` を付けてドラフトとして作成する（後でユーザーが公開可能）
- `$ARGUMENTS` がある場合はタイトルのヒントとして使う
- タイトルも命令形・動詞始まりの英語で書く（例: "Add Supabase DB migration for sketches table"）

## 禁止事項

- ユーザーの確認なしにIssueを作成しない
- 基準に当てはまらない指摘を、High（致命的）にしない
- フェーズ2の壁打ちを省略して下書きを作らない
- 5観点レビューをスキップしない
- 一度に複数の問いを重ねない
- 実装は行わない。フィードバックのみを提供する。
- ドラフトではなく正式なPRをユーザーの確認なしに作らない
- ポジティブな感想を必ずいれる。
