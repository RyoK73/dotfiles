## このスキルがやること

ステージ済みの変更を読み、`~/.gitmessage` のテンプレートに沿ったコミットメッセージ案を作る。
ユーザーの承認を得てからコミットする。
ステージ済みの変更がある場合は、ユーザーのステージを尊重し、`git add` / `git reset` で変更しない。
ステージ済みの変更がない場合のみ、このスキルが対象を決めてステージする（手順 1）。
push はしない。

## 手順

### 1. ステージ済みの変更を確認する

```
git diff --cached
```

**ステージ済みの変更がある場合**

- それだけをコミット対象にする。
- unstaged や untracked の変更は、メッセージの根拠にしないし、追加でステージもしない。

**ステージ済みの変更がない場合**

`git status --short` で変更一覧を確認し、次の順に対象を決める。

1. **会話の文脈から判断できる場合**: 会話で扱った変更（作成・編集したファイル）を対象にする。
2. **会話の文脈がない、または対象を特定できない場合**: 変更一覧を提示し、どれをコミットするかユーザーに質問する。返答を得てから進む。

対象が決まったら、ファイルをパスで指定してステージする。

```
git add -- <path>...
```

- `git add -A` / `git add .` / `git add -u` は使わない。対象外のファイルが混ざるため。
- 会話と無関係な変更（以前からの未コミットの変更など）は含めない。
- 1つのファイルに、対象の変更と無関係な変更が混ざっている場合は、そのファイルを含めてよいかユーザーに質問する。`git add -p` は対話式のため使わない。
- ステージしたファイルの一覧を、手順 3 の案とあわせてユーザーに示す。
- 変更が1件もなければ、「コミットする変更がありません」と伝えて終了する。

### 2. 分割の要否を判断する

ステージ済みの変更に、互いに無関係な内容が混ざっていないかを確認する。
混ざっていたら、手順 3 の案に「無関係な変更が混ざっているようです」と一言添える。
分割するかどうかはユーザーが決める。
ユーザーが元々ステージしていた変更は、勝手に分割したり、`git add` / `git reset` で変更したりしない。
分割する場合は、ユーザーがステージし直してから再度呼び出す。
このスキルがステージしたファイルについては、ユーザーの指示があれば `git restore --staged -- <path>` で外してよい。

**複数のファイルを、1つのコミットにまとめるか分けるかの基準**

目的が1つにつながっている変更でも、次の基準で分けるべきかを判断する。
基準が衝突したときは、番号の小さい基準を優先する。

1. **各コミットが単独で成り立つか**
   コミットごとに、ビルド・型・テストが通る単位にする。
   - テストは、検証する対象のコードと同じコミットにする。
   - 生成物（例: PNG）は、元データ（例: SVG）と同じコミットにする。
   - 依存される側のコミットを先にする。
   - ドキュメントは、実装が入ったあとのコミットに置く。実装前に、実装済みのように書いたドキュメントを入れない。
2. **revert の単位**
   「あとで戻すなら、どこから戻したいか」で分ける。
   戻すと副作用があるもの（`project_id`、マイグレーション、環境変数など）は、独立したコミットにする。
3. **変更の理由（Why）と type**
   Why が2つ書けるなら、分ける。
   type が違うもの（`feat` / `docs` / `chore` など）は、1つのコミットにしない。
   Why が1つで type も同じなら、まとめる。

**1つのファイルに複数の目的が混ざっている場合**
無理に分けず、ユーザーに質問する。`git add -p` は対話式のため使わない。

**分割案を作る場面**
- ステージ済みの変更をユーザーが用意していた場合: 分割しない。手順 3 の案に「分割したほうがよさそうです」と一言添えるだけにする。
- ステージ済みの変更がなく、このスキルが対象をステージする場合: 上の基準で分割案を作る。

### 3. メッセージ案を作る

`Read`ツールで`~/.gitmessage`を読んでその書式に従ってください。

引数に `wip` が渡された場合は、作業途中のコミットとして扱う。

- type を `wip` にする。
- 本文には、作業中のタスクを箇条書きで書く（`~/.gitmessage` の type 一覧の定義に従う）。

### 4. 案を提示して確認を得る

案を表示し、ユーザーの自由入力の返答を待つ。

- 承認（「OK」「ok」「はい」「LGTM」「お願いします」など）なら手順 5 に進む。承認かどうか曖昧な返答は、コミットせずに聞き返す。
- それ以外は修正指示として扱う。指示を反映して再提示し、承認を得るまで繰り返す。
- ステージ対象についての指示（「このファイルは外して」など）も修正指示として扱う。このスキルがステージしたファイルに限り、ステージを調整して再提示する。

**分割する場合の提示**

コミットごとに、ファイルの一覧とメッセージ案を、実行順に一覧で提示する。
承認は、一覧全体に対して1回で得る。
修正指示があれば、一覧を再提示する。

### 5. コミットする

HEREDOC で標準入力から渡してコミットする。
エディタは開かない。

```
git commit -F - <<'EOF'
<承認されたメッセージ>
EOF
```

コミット後、`git log -1 --stat` の結果を報告する。

**分割する場合**

承認された順に、次を繰り返す。
ステージの付け外しは、このスキルがステージしたファイルに限る。

1. `git reset -q` でステージを空にし、そのコミットのファイルだけを `git add -- <path>...` でステージする。
2. 上の HEREDOC でコミットする。

すべて終えたら、コミットごとの報告の代わりに、`git log -N --stat`（N はコミット数）でまとめて報告する。
各コミットを単独でチェックアウトしてのテスト実行は、既定では行わない。
報告には「各コミット単独の検証は未実施」と明記する。

### 6. コミットが失敗したとき

pre-commit hook などで失敗したら、エラー内容を報告する。
フォーマットなど自動修正できる原因なら、修正案を提示してユーザーの承認を得る。
修正後の再ステージは、ユーザーがステージしていた変更ならユーザーが行う。このスキルがステージした変更なら、このスキルが `git add -- <path>` で行ってよい。
`--no-verify` は使わない。

### 7. 次のフロー

- "Go Next","次"などの返答があれば、手順 1 にもどり、次のステージ済み変更を読み直してフローを再実行する
