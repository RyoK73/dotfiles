## このスキルがやること

ステージ済みの変更を読み、`~/.gitmessage` のテンプレートに沿ったコミットメッセージ案を作る。
ユーザーの承認を得てからコミットする。
ステージ済みの変更がある場合は、ユーザーのステージを尊重し、`git add` / `git reset` で変更しない。
ステージ済みの変更がない場合のみ、このスキルが対象を決めてステージする（手順 1）。
push はしない。

## 手順

### 1. ステージ済みの変更を確認する

```
git diff --cached
```

**ステージ済みの変更がある場合**

- それだけをコミット対象にする。
- unstaged や untracked の変更は、メッセージの根拠にしないし、追加でステージもしない。

**ステージ済みの変更がない場合**

`git status --short` で変更一覧を確認し、次の順に対象を決める。

1. **会話の文脈から判断できる場合**: 会話で扱った変更（作成・編集したファイル）を対象にする。
2. **会話の文脈がない、または対象を特定できない場合**: 変更一覧を提示し、どれをコミットするかユーザーに質問する。返答を得てから進む。

対象が決まったら、ファイルをパスで指定してステージする。

```
git add -- <path>...
```

- `git add -A` / `git add .` / `git add -u` は使わない。対象外のファイルが混ざるため。
- 会話と無関係な変更（以前からの未コミットの変更など）は含めない。
- 1つのファイルに、対象の変更と無関係な変更が混ざっている場合は、そのファイルを含めてよいかユーザーに質問する。`git add -p` は対話式のため使わない。
- ステージしたファイルの一覧を、手順 3 の案とあわせてユーザーに示す。
- 変更が1件もなければ、「コミットする変更がありません」と伝えて終了する。

### 2. 無関係な変更の混在を確認する

ステージ済みの変更に、互いに無関係な内容が混ざっていないかを確認する。
混ざっていたら、手順 3 の案に「無関係な変更が混ざっているようです」と一言添える。
分割するかどうかはユーザーが決める。
ユーザーが元々ステージしていた変更は、勝手に分割したり、`git add` / `git reset` で変更したりしない。
分割する場合は、ユーザーがステージし直してから再度呼び出す。
このスキルがステージしたファイルについては、ユーザーの指示があれば `git restore --staged -- <path>` で外してよい。

### 3. メッセージ案を作る

`Read`ツールで`~/.gitmessage`を読んでその書式に従ってください。

### 4. 案を提示して確認を得る

案を表示し、ユーザーの自由入力の返答を待つ。

- 承認（「OK」「ok」「はい」「LGTM」「お願いします」など）なら手順 5 に進む。承認かどうか曖昧な返答は、コミットせずに聞き返す。
- それ以外は修正指示として扱う。指示を反映して再提示し、承認を得るまで繰り返す。
- ステージ対象についての指示（「このファイルは外して」など）も修正指示として扱う。このスキルがステージしたファイルに限り、ステージを調整して再提示する。

### 5. コミットする

HEREDOC で標準入力から渡してコミットする。
エディタは開かない。

```
git commit -F - <<'EOF'
<承認されたメッセージ>
EOF
```

コミット後、`git log -1 --stat` の結果を報告する。

### 6. コミットが失敗したとき

pre-commit hook などで失敗したら、エラー内容を報告する。
フォーマットなど自動修正できる原因なら、修正案を提示してユーザーの承認を得る。
修正後の再ステージは、ユーザーがステージしていた変更ならユーザーが行う。このスキルがステージした変更なら、このスキルが `git add -- <path>` で行ってよい。
`--no-verify` は使わない。

### 7. 次のフロー

- "Go Next","次"などの返答により、次のステージ済み変更があれば、2.にもどりフローを再実行する
