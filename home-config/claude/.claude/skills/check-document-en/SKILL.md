## このスキルがやること

英語で書かれた文章を対象に、ネイティブスピーカーが読んで不自然に感じる箇所がないかをチェックする。
文法的な誤りだけでなく、その文書の種類における言い回しの癖や、充足度も対象にする。

## 対象の取得

- 引数として英文が渡された場合: それをそのままチェック対象にする。
- 引数がない場合: "チェック対象のドキュメント本文を入力してください。"と出力する。

## 文書の種類の判定

対象が次のどれに当たるかを、内容と会話から判定する。
判別できないときは、決めつけずにユーザーへ確認する。

- コミットメッセージ
- コードコメント・docstring
- README などの文書

## チェック観点

以下は代表的な着眼点で、これに限らない。

### 共通

- 冠詞(a/an/the)の過不足
- 前置詞の選択(for/of/toの誤用、不要な前置詞句)
- 単数・複数の一致
- 時制の混在
- 冗長な表現(圧縮できる複合名詞をわざわざ前置詞句にしているなど)
- スペル・タイポ

### コミットメッセージ

- `Read` で `~/.gitmessage` を読み、その書式(type、件名、Why / What)を基準にする。
- タイトル行(1行目)は、簡潔さと動詞の形が重要になりやすいので、特に注意する。
- 命令形を要求するのはタイトル行のみとする。
- 本文(What、Why などの箇条書き)は、現在形・過去形・命令形のいずれも、それだけでは誤りとして扱わない。

### コードコメント・docstring

- コメントの形(完全な文か、句か)が、同じファイルの中で統一されているか。
- 対象のコードが会話やファイルから確認できる場合、コードの内容と食い違う記述がないか。
- 識別子(関数名・変数名)の綴りは、指摘の対象にしない。

### README などの文書

- 見出しの形(名詞句か、動詞始まりか)が統一されているか。
- 手順の文が命令形で統一されているか。
- 同じものを指す用語の表記が揺れていないか。

問題が見当たらない場合は、無理に指摘をひねり出さない。「問題ありません」とだけ伝えて終える。

## 出力形式

必ずこの順序・粒度で、簡潔な箇条書きとして出す。長い説明文にはしない。
修正文を最初に提示し、その後に指摘を述べる。

```markdown
## 修正文

<書き直した完全な文章>

- 多岐にわたる場合、見出しごとに記述
- 元の文章の構成・順序・内容は変えず、指摘した箇所だけを直す

### 追記案

<元の文章に書かれていない、不足している項目の追記案>

- 修正文の続きとして、不足している項目だけを書く
- コミットメッセージの場合は、`~/.gitmessage` の Why / What のうち欠けているものを対象にする
- 追記案が不要な場合(すでに十分書かれている場合)は、このセクション自体を省略する

## 指摘

- "<問題のある箇所>" → <何がどう不自然か、一言>
- (指摘が複数あれば列挙。なければ「特に問題ありません」の一行のみ)
```

## 注意点

- 複数行の本文がある場合、タイトル行と本文で指摘を分けて構わない。
- 修正文を提示する際、元の文章が伝えようとしている内容を変えない。文法・言い回しの修正に留め、意味を変えるような書き換えはしない。
- 修正文と指摘は必ず対応させる。
  - 修正文で変えた箇所は、すべて指摘に挙げる。
  - 指摘していない箇所は、修正文で変えない。
  - 構成の入れ替え(What と Why の順序など)や、文の言い換え・追加を黙って行わない。
- 指摘の根拠は、誤りと好みで区別する。
  - 文法・語法上の誤りは、指摘として断定してよい。
  - プロンプト・スキル・ドキュメントに書かれていない規則を、あたかも決まりであるかのように述べない。
- 元の文章の意図が曖昧で、複数の解釈が成り立つ場合は、修正文でどちらかに決めつけず、解釈を明記して確認を促す。
- 不足している記述は、指摘ではなく「追記案」として修正文の後に提示する。
  - 追記案は、会話・差分から確認できる事実に基づいて書く。確認できない内容は推測と明記する。
