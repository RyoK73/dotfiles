## 壁打ちフェーズ

この計画のあらゆる側面について、共通理解に達するまで容赦なくインタビューを行う。設計ツリーの各分岐を一つずつ辿り、決定間の依存関係を順番に解決していく。

質問は一度に一つずつ行うこと。

コードベースを調べることで答えられる質問がある場合は、インタビューの代わりにコードベースを調べること。

壁打ちの中で、機能を次の2種類に分けて把握しておくこと。

- リスクが高い部分: 計算ロジック、権限判定、データ変換、状態遷移など、間違えると気づきにくいもの
- リスクが低い部分: 画面の見た目、ボイラープレート、設定ファイル、使い捨てのスクリプトなど

次の点についても確認すること

- ファイル・ディレクトリ構成

## テスト項目フェーズ

壁打ちが完了したら、リスクが高い部分についてテスト項目を作る。テスト項目はユーザーが決める仕様であり、Claudeが推測で埋めるものではない。

- この段階ではテストコードを書かない。テスト項目の一覧だけを出す
- 形式は「入力・条件 → 期待する結果」の表にする
- 正常系に加えて、境界値と異常系も含める
- 一覧はまとめて提示し、ユーザーにレビューしてもらう(この段階に限り「質問は一度に一つ」の例外とする)
- 期待する結果が曖昧で決められない項目は、推測で埋めずにユーザーへ質問する
- ユーザーが承認した一覧を「確定した仕様」とする
- リスクが低い部分にはテスト項目を作らない(その旨を一覧の末尾に明記する)

## 壁打ち内容の保存（実装方法を問わず必須）

壁打ち内容を、本体リポジトリの `.git` 直下に保存する。
コミット対象や `.gitignore` に影響させない。
worktree で実行しても、全worktreeの壁打ち内容が本体の `.git` に集まる。

```bash
dir="$(git rev-parse --path-format=absolute --git-common-dir)/grill-me"
mkdir -p "$dir"
file="$dir/$(date +%Y-%m-%d)-{テーマのスラッグ}.md"
```

ファイル名: `{YYYY-MM-DD}-{テーマのスラッグ}.md`

フォーマット:

```markdown
---
date: { YYYY-MM-DD }
tags: [grill-me]
repository: { repository-name }
---

# {テーマ}

## 概要

{壁打ちフェーズで確定した内容のうち全体に通じること・前提次項を記述する}

## 対応ファイル

- [ ] `<ファイルパス>`
- [ ] `<ファイルパス>`
- [ ] `<ファイルパス>`

### ファイルツリー

ファイルツリー

### `<ファイルパス>`

{作成されるファイルごとの決定事項を記述する}

#### テスト項目

{承認された「入力・条件 → 期待する結果」の表}

### `<ファイルパス>`

{作成されるファイルごとの決定事項を記述する}

#### テスト項目

{承認された「入力・条件 → 期待する結果」の表}
```

保存後、ファイルの絶対パスをテキストで表示する（`file://` は付けない）。

## 実装方法の選択

テスト項目フェーズが完了したら、必ず`AskUserQuestion`で次を確認する。

- 「claudeが実装する（作成したドキュメントを元にプランモードで進める）」
- 「自分で実装する」

### claude 実装

その後、プランモードで実行する。
{壁打ちフェーズ}と{テスト項目フェーズ}の結果をもとに実装計画を立て、次の順序で進める。

1. 確定したテスト項目を、そのままテストコードにする。テスト実行コマンドは `CLAUDE.md` やプロジェクト設定から調べる
2. 実装の前にテストを実行し、失敗(Red)を確認する。失敗理由が「未実装」であることを確認して報告する。期待値の食い違いなど、別の理由で落ちている場合は実装に進まず、ユーザーに報告する
3. テストを通す実装を行う。複数ファイルをまとめて作ってよい。テスト項目とテストコードは変更しない。テストが通らず、テスト側の問題が疑われる場合も、修正せずに理由を報告してユーザーの判断を待つ
4. 全テストが通ったら、テスト結果と変更ファイルの差分を要約して報告する

リスクが低い部分は、テストなしでまとめて実装してよい。

## 終了（ユーザーが実装する場合）

コードは一切書かない。保存したドキュメントのパスを再度案内してセッションを終了する。
