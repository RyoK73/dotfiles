# add-rule

言語・フレームワーク・ツールごとのこだわりを、グローバルのrulesファイルに追記する。
対象のファイルを扱うときだけ読み込まれるように、`paths` 付きで管理する。

## 引数

```
$ARGUMENTS
```

- **引数あり**: その内容を、追加するルールとして扱う。
- **引数なし**: 追加したいルールの内容を質問する。

## 前提

- 保存先は、dotfiles側の `~/dev/dotfiles/home-config/claude/.claude/rules/` とする。
  - `~/.claude/rules/` はdotfilesへのシンボリックリンクで管理されている。
  - `~/.claude/rules/` に直接作ると、dotfilesの管理外になるため、そこには作らない。
- 対象は、グローバルのrulesのみとする。プロジェクトの `.claude/rules/` は扱わない。
- インデックスファイルは作らない。
- サブディレクトリは使わず、`~/.claude/rules/` 直下にフラットに置く。
  - ユーザーレベルのrulesで、サブディレクトリが読み込まれるかは、公式ドキュメントで未確認のため。

## 手順

### Step 1: 入力の解釈

以下を特定する。

- ルールの内容。
- 対象の言語・フレームワーク・ツール。

対象が複数に解釈できる場合や、特定できない場合は、決めつけずにユーザーへ質問する。

### Step 2: 種別・ファイル名・paths の決定

| 種別 | ファイル名 | 例 |
|---|---|---|
| 言語 | `lang-{言語}.md` | `lang-typescript.md` |
| フレームワーク・ツール | `tool-{名前}.md` | `tool-react.md`, `tool-docker.md` |
| 言語・ツールに依存しない方針 | 既存の `develop/` 配下のファイルに追記する | `develop/naming.md` |

`paths` は、次の表から決める。

| 対象 | paths |
|---|---|
| typescript | `**/*.ts`, `**/*.tsx` |
| javascript | `**/*.js`, `**/*.jsx`, `**/*.mjs` |
| python | `**/*.py` |
| lua | `**/*.lua` |
| go | `**/*.go` |
| rust | `**/*.rs` |
| shell | `**/*.sh`, `**/*.zsh` |
| react | `**/*.tsx`, `**/*.jsx` |
| docker | `**/Dockerfile*`, `**/compose*.y*ml` |

- 表にない対象は、ユーザーに対象の拡張子やファイル名を質問して決める。
- 決まった対応は、このSKILL.mdの表に追記して、次回以降に使えるようにする。
- `paths` は、YAMLのリストで書き、各globをダブルクォートで囲む。
- `paths` の基準ディレクトリは、セッションのprimary working directoryである。

### Step 3: 既存ルールの確認

- `Glob` で `rules/**/*.md` を列挙する。
- 同じ対象のファイルがあれば、`Read` して内容を把握する。
- 重複・矛盾の確認のため、`paths` なしの全体ルール（`develop/` 配下、`documentation.md` など）も `Read` する。

### Step 4: 重複・矛盾の検出

- 同じ意味のルールがすでにあれば、**重複**として扱い、追記しない。その旨を報告する。
- 既存のルールと反対の内容であれば、**矛盾**として扱い、どちらを優先するかをユーザーに確認する。
  - 既存を置き換える場合は、置き換える行を明示する。

### Step 5: 提案と承認

書き込む前に、以下を提示して承認を得る。

- 保存先のファイル（新規か追記か）。
- `paths`。
- 追記するセクション。
- 追記する内容。

### Step 6: 書き込み

- **新規作成**: `Write` で、下記のテンプレートから作る。
- **追記**: `Edit` で、該当するセクションに1行追加する。

#### 言語別ファイルのテンプレート

見出しだけを固定する。
内容がないセクションは省略する。

````markdown
---
paths:
  - "{glob}"
---

# {言語名}

## 標準ライブラリ・APIの選択

## 型・データ構造の方針

## 命名

## 禁止事項
````

ルールは、1行1事項で書く。
必要なら、理由を添える。

例:

```markdown
- 日付・時刻は `Date` ではなく `Temporal` を使う。（理由: タイムゾーンの扱いが明示的になるため）
```

ツール別ファイルも、同じテンプレートを使う。

### Step 7: 反映の確認

- `~/.claude/rules/` に、該当ファイルのリンクがあるか確認する。

```bash
ls -l ~/.claude/rules/
```

- リンクがなければ、以下のstowコマンドを案内する。実行は、ユーザーの承認を得てから行う。

```bash
stow -d ~/dev/dotfiles/home-config claude
```

### Step 8: 完了報告

以下の形式で報告する。

```
追加しました: {保存先のパス}
種別: {言語 | ツール | 全体} | paths: {globの一覧}
内容: {追加したルール}
反映: {リンク済み | stowが必要}
```

## 注意

- 読み込まれるのは、対象のファイルを Read / Write / Edit したときである。
  - 対象の拡張子のファイルがまだないセッションでは、読み込まれない可能性がある。
- YAMLが解析できないfrontmatterは無視され、`paths` なしのrulesとして全体に読み込まれる。
  - 書式を崩さないように注意する。
- 読み込み状況を確認したいときは、`claude --debug` か `InstructionsLoaded` フックのログを使う。
